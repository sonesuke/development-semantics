# Validationのモデル

Validationは、Requirementsを起点に、要求・仕様が利用者の目的・利用状況に適するかを評価する。この知識体系では、要求を基準として実装の適合を問う[Verification](../verification/model.md)と区別する。

以下では、明示した利用状況のすべてで、許容する結果だけが生じることを適合条件とする。これは目的への適合を扱うための一つのモデルであり、確率的な成功率や期待効用を直接扱うものではない。

## Requirementsを起点とする問い

Requirementsは、目的と実装の間に置く共通の起点である。Validationはそこから目的・利用者の必要へ向かい、Verificationは実装へ向かう。

Validationでは、実装が要求を満たすことを今回の検討の仮定として固定し、「要求どおりに実現したとして、その要求で目的を達成できるか」を疑う。要求は、目的を基準に妥当性を問われる対象である。

ここでVerificationを前提とするとは、実装の適合を証明済みとみなすことではない。実装の不具合をいったん切り離し、要求そのものを評価するための仮定である。要求策定時のように実装がまだなくても、この問いは成立する。

反対に[Verification](../verification/model.md#requirementsを起点とする問い)では、要求の妥当性を仮定して実装を疑う。両者は互いの結論を根拠として循環的に証明する関係ではなく、固定する仮定と疑う対象を切り替える関係である。

## 評価の構造

評価の枠組みを次の組で表す。

\[
F=(U,N,C,A,O,G,\Pi)
\]

| 記号                    | 定義                                                                        |
| ----------------------- | --------------------------------------------------------------------------- |
| \(U\)                   | 評価で扱う利用者・関係者の集合                                              |
| \(N\)                   | 誰の、どの問題を解決したいかを記述する目的・必要の集合                      |
| \(C\)                   | 利用者、タスク、環境、運用上の制約を含む利用状況の集合                      |
| \(A:C\to\{\top,\bot\}\) | 評価が依拠する前提                                                          |
| \(O\)                   | 利用結果の集合。成功だけでなく失敗、拒否、未完了も含む                      |
| \(G\)                   | 各 \(g:C\times O\to\{\top,\bot\}\) が、目的に関する達成条件を表す述語の集合 |
| \(\Pi\)                 | 各達成条件の真偽を、結果の受け入れ可否へ集約する方針                        |

\(U,N,C,G\) は空でないものとする。\(G\) の各条件には、対応する \(U\) の関係者と \(N\) の目的を明示する。結果には、所要時間や利用者の負担など、判断に必要な観測も含める。

評価対象となる利用状況と、そこで目的に適するとみなす結果の集合を定義する。

\[
C_A=\{c\in C\mid A(c)\},\qquad C_A\ne\varnothing
\]

\[
O_F(c)=\{o\in O\mid\Pi((g(c,o))_{g\in G})=\top\}
\]

例えば全条件を必須にする場合、\(\Pi\) は連言である。目的が競合する場合は、優先順位や許容する不利益を \(\Pi\) に反映する。条件を単に列挙するだけでは、競合時の判断は定まらない。

この定義は、選んだ \(G,\Pi\) のもとでの適合を扱う。\(G,\Pi\) が実際の必要 \(N\) を十分に反映するかは別途根拠を要し、記号を置くだけでは保証されない。

## 要求・仕様の適合

要求・仕様 \(R\) が利用状況 \(c\) で許容する結果を \(O_R(c)\subseteq O\) とする。実装の結果集合と比較する際には、同じ利用状況と観測の粒度を用いる。

\[
\operatorname{FitReq}(R;F)
\iff
\forall c\in C_A,\quad
\varnothing\ne O_R(c)\subseteq O_F(c)
\]

これは、要求が許容する結果なら目的にも適する、という十分条件を定義する。非空性は各利用状況で許容結果が存在することを要求するが、すべての利用状況を扱える実装の存在までは示さない。

例えば要求が残高の非負性だけを規定するなら、正当な出金を拒否する結果も \(O_R(c)\) に含まれ得る。その結果が \(O_F(c)\) に含まれなければ、\(\operatorname{FitReq}(R;F)\) は成立しない。特定の実装が目的に適していても、要求自体は目的の達成を十分に制約していない場合がある。

## 要求と実装を合わせた目的への適合

要求の妥当性と実装の適合が組み合わされた結果を表すため、実現された振る舞いの目的への適合も定義する。この条件だけでは、不適合の原因が要求にあるのか実装にあるのかは決まらない。

対象の特定の版を \(x\)、利用状況 \(c\) でその対象から生じ得る結果を \(T_x(c)\subseteq O\) とする。設計や試作を対象にする場合は、そのモデルが表す結果集合を用い、実装との対応は別途確認する。

\[
\operatorname{Fit}(x;F)
\iff
\forall c\in C_A,\quad
\varnothing\ne T_x(c)\subseteq O_F(c)
\]

つまり、対象となる各利用状況で結果が存在し、そのすべてが目的に適する。結果集合を空にして条件を自明に満たすことを避けるため、非空性を要求する。対象が完了しない場合は、結果を存在しないものとせず、未完了として \(O\) に含める。

例えば出金の結果に「残高」「要求した出金の成否」「所要時間」を含める。「残高が負にならない」だけを満たしても、正当な出金をすべて拒否するなら、業務の成立を求める達成条件は満たさない。

## 適合の主張と証拠による判断

\(\operatorname{Fit}\) と \(\operatorname{FitReq}\) は結果集合についての意味論的な条件であり、観測済みの結果だけについての条件ではない。

証拠 \(E\)、受け入れ規則 \(K\)、適合についての命題 \(\varphi\) に対する判断を次のように表す。

\[
E\vdash_{K,F}\varphi
\]

これは、枠組み \(F\) と規則 \(K\) のもとで、証拠 \(E\) が \(\varphi\) を受け入れるのに十分だと判断したことを表す。この判断関係は、ここではパラメータであり、一般的な推論規則や健全性を定義したものではない。

評価記録には、対象の版、\(F\)、\(\varphi\)、\(E\)、\(K\) と判断結果を残す。利用観察、試作の評価、利用状況に即した試験、運用結果などを、どの条件を支持するかに対応付ける。関係者の合意だけで、実際の結果が目的に適するとは結論しない。

観測した利用状況を \(C_{\mathrm{obs}}\subseteq C_A\)、そこで観測した結果を \(T_{\mathrm{obs}}(c)\subseteq T_x(c)\) とする。

\[
\bigl(\forall c\in C_{\mathrm{obs}},\quad
T_{\mathrm{obs}}(c)\subseteq O_F(c)\bigr)
\ \not\Rightarrow\ \operatorname{Fit}(x;F)
\]

未観測の利用状況や結果が残り得るためである。一般化には、代表性や対象モデルに関する追加の根拠が必要になる。一方、\(c\in C_A\) で実際に生じ得る \(o\in T_x(c)\) が \(O_F(c)\) に含まれなければ、その反例によって \(\operatorname{Fit}(x;F)\) は否定される。

## Verificationとの接続

要求を固定して実装を疑う条件は、[Verificationの適合条件](../verification/model.md#結果集合による適合条件) \(\operatorname{Conforms}(x,R;C_A)\) で定義する。Validationでは、要求が許容する結果を目的に照らす \(\operatorname{FitReq}(R;F)\) を問う。集合の包含関係の推移性から、次が成り立つ。

\[
\operatorname{Conforms}(x,R;C_A)
\land\operatorname{FitReq}(R;F)
\Rightarrow\operatorname{Fit}(x;F)
\]

要求への適合だけでは、\(O_R(c)\subseteq O_F(c)\) は示せない。また、目的に適する特定の結果を観測しただけでは、要求が規定するすべての性質への適合は示せない。同じ証拠を両者で使う場合も、支持する命題を区別する。

## 有効範囲と再評価

適合の主張は \(x\) または \(R\) と、枠組み \(F\) に依存する。対象の版、目的、利用状況、前提、達成条件、集約方針が変われば、以前の結論をそのまま適用できるとは限らない。

例えば、対象と結果の意味を固定し、評価範囲だけを \(C_A'\subseteq C_A\) に狭める場合、成立済みの適合条件は非空な新しい範囲でも成立する。逆に範囲を広げる場合は、追加した利用状況についての論証が必要になる。

要求を見直した場合は、Verificationの検証責務と既存の証拠の適用範囲も見直す。ValidationとVerificationを、開発の段階によって一度だけ順に実施するものとはしない。

達成条件の根拠、証拠による判断規則、確率的な評価への拡張は、[未定義事項](./open-questions.md)として残る。
