# PRの構成戦略

戦略は、[モデル](./model.md)の受け入れ条件を満たすために、変更の分割・提示順序・情報の配置を選ぶ方法である。適用したことだけで正当性や負荷の改善が保証されるわけではない。

## 選択の手順

1. 要求をClaimsへ分解し、BehaviorとImplementationへの対応を示す。
2. [Verificationのモデル](../verification/model.md)に従い、変更と維持すべき性質からVOを導出し、網羅性と証拠の十分性を確認する。
3. 論証とBehaviorの境界をもとにPRとCommitの分割候補を作る。
4. 情報の有効条件・アクセス経路・検証可能性から配置を選ぶ。
5. 各候補の受け入れ条件を確認し、Review LoadとRepository Loadを別々に比較する。

要求や利用上の前提を変更する場合は、[Validation](../validation/model.md)による目的への適合の評価も行い、その結果をClaimsとVOに反映する。

必要な論証と証拠は要求・変更・既存の性質・Repository Rulesに依存する。すべてのPRに同じ文書量や形式的証明を要求しない。

## PR分割と階層化

PRの分割境界は、Claimの論証境界とBehaviorの変更境界が一致する箇所を第一候補とする。

\[
\mathcal R_i\rightarrow\mathcal Q_i
\rightarrow\mathcal B_i\rightarrow\mathcal I_i
\]

各PRが対応する部分構造を担当する。ファイル数や差分の行数だけでは、論証が完結する境界は決まらない。

### 分割の評価

1. Claimの論証が部分構造内で完結するか。
2. Behaviorの変更が独立しているか。
3. Implementationの変更を分離できるか。
4. Verificationを独立して実施できるか。
5. 境界をまたぐ依存関係が明示されているか。

共通の前提や不変条件は、補題やインターフェースとして切り出せる。外部の前提への依存があることと、論証が未完了であることは同一ではない。何を前提として利用できるか、その根拠にどこからアクセスできるかを明示する必要がある。

ただし、これは部分構造の閉包性の厳密な定義ではない。論証が完結する条件と、依存先に何を要求するかは[未定義事項](./open-questions.md)として残る。

**適用条件と負担**：各部分の前提・証拠・依存先を明示できる場合に分割候補とする。分割で一度に追う論証を減らせても、PR間の参照や統合時の検証責務が増える場合がある。

### CommitとPR

Commitは、一つのPR内で変更と論証を順序付きに提示する単位にもなる。共通の前提を先に導入し、その前提を利用する変更を後に置くなど、[予定調和](#予定調和)に沿って構成する。

PRの独立した受け入れ判断と、Commitの読み進めやすさは区別する。Commitの数を増やすだけでは、論証の分割や認知負荷の改善は保証されない。

### Merge Branchによる階層化

Merge Branchは、複数のPRを上位目的のもとで統合する構造として扱う。

個別PRの正当性に加えて、合成後のBehaviorがRequirementsを満たすことを論証する。個々のPRが正しくても、共有状態、インターフェース、実行順序などへの相互作用によって、合成後の性質が保存されるとは限らない。

必要に応じて、互換性、非干渉性、共有する不変条件、統合時の検証責務を明示する。Behaviorの独立性と安全な合成の一般的な条件は、まだ形式化していない。

## 論証の提示順序

関心とは、現在追跡している命題、Requirements、目的である。同じ目的について、要求から証拠までの論証が連続することが望ましい。

\[
r_1\rightarrow q_1\rightarrow b_1\rightarrow i_1
\rightarrow \text{Evidence}_1
\]

ファイルや技術レイヤーが変わっても、目的が連続していれば、必ずしも関心の切り替えではない。ファイル単位のまとまりと、論証単位のまとまりは区別する。

### 予定調和

予定調和とは、次に必要な情報が、それまでの理解から自然に予測でき、必要な時点で提示されることである。

- 前提が利用可能な順序で論証する。
- 同じ目的についての論証を可能な限り連続させる。
- 共通の前提を補題として切り出し、再利用する。
- 明示的な参照によって、不要な先読みを避ける。
- 不必要な重複や往復を避ける。

この考え方を、Commit分割、PR分割、Bodyの構成、参照の配置に適用する。参照を増やすこと自体が目的ではなく、必要な前提と証拠へ自然に到達できる構造を作る。

**適用条件と負担**：必要な前提と証拠を保って並べ替えられる場合に用いる。目的を連続させることで探索や前提保持を減らせる可能性がある一方、共通前提の重複や参照の往復が増えることもある。

切り替え、記憶、推論の順に重視するのは設計仮説であり、経験的に確立した普遍的な順位ではない。実際の読者とタスクに照らして判断する。

## 知識の配置

状態についての知識はRepositoryに、状態遷移についての知識はPRに置く。この原則は、情報が有効である条件に基づく出発点である。具体的な媒体は、アクセス経路と検証可能性も含めて決定する。

\[
S_0\xrightarrow{P}S_1
\]

| 観点     | 状態についての知識                 | 遷移についての知識                |
| -------- | ---------------------------------- | --------------------------------- |
| 説明対象 | 状態 \(S_1\)                       | 特定の遷移 \(S_0\rightarrow S_1\) |
| 主な問い | 現在どう動作するか、なぜそうなのか | なぜ変更したか、変更してよいか    |
| 有効条件 | 実装・契約・前提が維持されること   | 特定の変更が対象であること        |
| 主な読者 | 将来の開発者                       | 変更をレビューする人              |

### 有効条件を明示する

有効性の定義は[モデル](./model.md#情報の有効条件)に従う。

例えば、「この設定では、未宣言のcaskと関連データが削除される」は設定の動作についての知識であり、将来のコード理解にも必要となる。一方、「今回の変更では、削除対象のcaskがないことを確認した」は特定の遷移に関する検証結果であり、PRに属する。

外部環境に依存する説明では、有効条件を具体的に残す。例えば、次のコメントは仮のバージョン条件の記述例である。

```text
# unstable until stable ships gh >= 2.103
```

条件を記述することと、その条件が変化したときに検知することは別である。外部状態を取得して検証できるなら、CIなどによる確認も考えられる。

### 配置の二段階

第一段階では、情報がどの状態・遷移・外部環境について有効なのかを判断する。第二段階では、参照対象と論証上の役割を踏まえ、次の三つの観点を組み合わせて媒体と表現を決める。

| 観点         | 問い                                         |
| ------------ | -------------------------------------------- |
| 有効条件     | どの状態・遷移・外部環境について正しい情報か |
| アクセス経路 | 将来、誰がどこからその情報を探すか           |
| 検証可能性   | その知識を機械的に検証・維持できるか         |

「状態についての知識だからCode Comment」という結論は、この第一段階だけからは導けない。[Working Tree・Git History・PR Record](./model.md#知識の保持)の経路を踏まえ、テスト、設定、設計文書、Code Comment、Commit Message、Body、Inline Comment、CIなどへの配置を考える。

### 実行可能な制約と説明

機械的に検証可能な性質は、可能な限り実行可能な制約として保持する。検証できない前提や理由は、明示的な説明として保持する。

| 知識の例                                       | 保持する表現の候補                       |
| ---------------------------------------------- | ---------------------------------------- |
| 残高が負にならない                             | テスト、型・制約、形式的証明など         |
| APIが旧バージョンと互換である                  | 契約テスト、互換性の契約                 |
| 運用上の制約からアルゴリズムを選んだ           | 設計理由とその前提の説明                 |
| 外部ライブラリが条件を満たしたら実装を変更する | 有効条件の説明と、可能なら条件のチェック |

Executable Check、Code Comment、Documentationを全順序にはしない。それぞれ表現できる知識が異なる。テストが「何を満たすか」を示しても、「なぜそれを要求するか」の説明が必要な場合はある。

### 複数の目的に必要な知識

設計選択の理由のように、PRの受け入れ判断にも将来のコード理解にも必要な情報は、Repositoryに保持し、PRから参照する構造を考えられる。PR Recordに詳細を残す場合も、将来の利用者が必要な箇所から辿れるようにする。

例えば、「CIのジョブ名がルールセットと一致している」という性質は、コメントで宣言するより、一致を自動検証する方が適する場合がある。Colimaを選んだライセンス上の理由が将来にも必要なら保持するが、その設定行の直上に置くことが常に最適とは限らない。

これらは配置判断の例であり、特定のPRや実際の設定について検証済みであることを意味しない。配置の目的は、[必要な知識の保持](./model.md#知識の保持)と、[Review Load・Repository Load](./model.md#認知負荷)の双方における不要な探索や冗長性の抑制である。

## 証拠への参照

証拠はBodyだけに集約する必要はない。Diff、テスト、CI Results、設計文書、Commentsなどを明示的に参照し、命題から証拠を追跡できるようにする。[物理的な配置](./model.md#prの物理的構造)と論証上の役割は分離する。

## マージ後のアクセス経路

CodeからCommit、CommitからPRを辿るには、その対応がマージ後も維持されている必要がある。Squash MergeやRebase MergeなどによってCommit IDや履歴構造が変わり得るため、マージ前の参照がそのまま有効であるとは限らない。

Commit Messageには、将来の利用者が変更理由を理解するための最小限の情報と、必要に応じてPRへの参照を残す。保持を評価するときは、作業中のCommitだけでなく、採用するマージ方法によって残る履歴を対象にする。

**適用条件と負担**：将来必要な知識と探索の開始点を特定し、採用するマージ方法のもとで経路を確認する。参照は説明の重複を減らせるが、探索や外部サービスへの依存を増やす場合がある。

## 候補の比較

同じ論証と必要な知識へのアクセスを維持したまま、目的の切り替えや不必要な前提保持を減らせるなら、その構造を優先できる。

一方、切り替えを減らすと重複が増えるなど、複数の指標が競合する場合もある。一意の最適解が存在するとは限らず、非支配な構造の扱いは[未定義事項](./open-questions.md)である。

[Repository Loadの不変性](./theorems.md#同じ最終状態とアクセス経路でのrepository-load)は、最終状態とアクセス経路が同じ場合に限る。PRの読みやすさが改善しても、将来のリポジトリ理解の負荷が改善したとは限らない。
