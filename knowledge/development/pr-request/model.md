# PRのモデル

PRを、要求から実装への変更、その正当性を支持する論証、情報の物理的な配置として定義する。定義から導く性質は[定理](./theorems.md)、分割・提示・配置の選択は[戦略](./strategies.md)で扱う。

## 変更の意味論

ソフトウェア変更を、内部関係を持つ四つの構造と、それらの間のマッピングとして扱う。

\[
\mathcal R \xrightarrow{M_{RQ}} \mathcal Q
\xrightarrow{M_{QB}} \mathcal B
\xrightarrow{M_{BI}} \mathcal I
\]

| 記号           | 構造           | 主な要素                     |
| -------------- | -------------- | ---------------------------- |
| \(\mathcal R\) | Requirements   | 要求、制約、依存関係         |
| \(\mathcal Q\) | Claims         | 命題、前提、補題、含意       |
| \(\mathcal B\) | Behavior       | 状態、操作、遷移、不変条件   |
| \(\mathcal I\) | Implementation | コード、型、データ、実行関係 |

各構造は要素の集合だけでなく内部関係を持つ。マッピングは多対多になり得るため、一般には関数ではなく関係として扱う。対応先が存在することと、その対応が正しいことは区別する。

### RequirementsからClaimsへ

要求を、検証可能な命題へ分解する。例えば「出金処理を安全にする」という要求に対して、次のClaimsを置く。

- \(q_1\)：残高が負にならない。
- \(q_2\)：有効な出金が正常に実行される。
- \(q_3\)：同時出金でも整合性が保たれる。

分解されたClaimsは、明示した前提のもとで、元のRequirementsを十分に支持する必要がある。

\[
q_1 \land q_2 \land q_3 \Rightarrow r
\]

この含意は、Claimsを列挙するだけでは成立しない。「安全」の範囲や有効な出金の条件を定め、分解が要求を支持すること自体を論証する。

### ClaimsからBehaviorへ

Claimsを、状態と操作に関する性質へ翻訳する。

\[
\mathcal B=(S,O,\delta)
\]

例えば、残高の非負性を有効な状態の集合 \(S_{\mathrm{valid}}\) として表し、遷移による保存を要求する。

\[
\forall s\in S_{\mathrm{valid}},\ \forall o\in O,
\quad \delta(s,o)\in S_{\mathrm{valid}}
\]

この表現は、\(\delta\) が対象操作について定義されていることを前提とする。操作に事前条件がある場合は、適用可能な操作を量化の対象にするか、拒否される操作の振る舞いもモデル化する。

### BehaviorからImplementationへ

抽象的なBehaviorと、実際のコード・型・データ・実行関係を対応付ける。

\[
\mathcal I\sqsubseteq\mathcal B
\]

ここで \(\sqsubseteq\) は、実装が抽象的なBehaviorを具体化する関係を表す。どの観測・操作・実行を対応付けるかは、対象に応じて定める。対応の正当性は、設計、テスト、形式的証明などによって論証する。

### 性質保存

各マッピングの共通条件は、必要な性質が失われないことである。

\[
\operatorname{Preserves}(M_{XY},\Phi_{XY})
\]

\(\Phi_{XY}\) は、そのマッピングで保存すべき性質を表す。構造ごとに表現方法が異なるため、同じ式をそのまま移すことだけを意味しない。保存すべき性質と保存関係の一般的な定義は、[未定義事項](./open-questions.md)として残る。

### PRが扱う状態遷移

PRは、リポジトリ状態の変更を扱う。

\[
(\mathcal R_0,\mathcal B_0,\mathcal I_0)
\xrightarrow{P}
(\mathcal R_1,\mathcal B_1,\mathcal I_1)
\]

この表記は意味論上の主要要素を示したものであり、リポジトリ状態の全内容を列挙するものではない。Claimsはこの対応を支持する[論証](./model.md#論証と検証)で扱う。

PRは、変更後の実装がRequirementsを満たすことと、維持すべき既存の性質が失われないことを論証する。局所的な正しさに加え、必要に応じて既存Behaviorとの合成、互換性、非干渉性を扱う。

要求の出所や、要求を採用した理由の正当性は、評価の前提とする。一方、与えられた要求に対して、その設計・実装を選択した理由はPRの論証対象である。

## 論証と検証

論証とは、[構造間のマッピング](./model.md#変更の意味論)が要求される性質を保存していることを、命題・前提・推論・証拠によって支持するものである。

論証グラフを次のように表す。

\[
G_A=(N_A,E_A)
\]

ノードはClaims、前提、補題、Verification Obligations、証拠などであり、辺は論理的な依存関係や明示的な参照である。単なる参照が論理的な支持を意味するとは限らないため、どの証拠がどの命題を、どの前提のもとで支持するかを区別する。

### Verificationの対象

主要な検証対象は、BehaviorがRequirementsを満たすことと、ImplementationがBehaviorを具体化することである。

\[
\mathcal B\models\mathcal R
\qquad
\mathcal I\sqsubseteq\mathcal B
\]

要求をClaimsへ十分に分解できているかも論証対象である。上の二式だけで、要求の解釈や分解の妥当性が自動的に保証されるわけではない。

### Verification Obligations

Verification Obligation（VO、検証責務）は、Requirements、変更内容、維持すべき既存の性質、Repository Rulesから導出する。Repository Rulesは、そのリポジトリで受け入れに必要とされる規則を指す。

各VOには、対象となる命題、前提、対応する変更、証拠への参照、現在の状態を対応付ける。

| 状態     | 意味                                                           |
| -------- | -------------------------------------------------------------- |
| Verified | 適用する受け入れ基準のもとで、十分な証拠によって支持されている |
| Deferred | 検証を後に延期している                                         |
| Waived   | 適用する規則と判断に基づいて、検証を免除している               |
| Open     | 検証が完了しておらず、延期・免除としても整理されていない       |

DeferredとWaivedはVerifiedを意味しない。延期・免除の理由や条件を明示し、受け入れ可能かはRepository Rulesと要求に照らして判断する。状態ラベルだけで受け入れ可否を決定しない。

### 網羅性と証拠の十分性

次の二つを別々に評価する。

- VOの網羅性：要求・変更・既存の性質・規則から必要な責務を導出できているか。
- 証拠の十分性：各VOを支持する証拠が、その適用範囲と前提のもとで十分か。

テスト成功は、実装の振る舞いに関する証拠である。すべての状態についての形式的証明とは区別する。また、個別の証拠が強くても、必要なVOが欠けていればPR全体の十分性は得られない。

設計説明・テスト・形式的証明は、支持できる命題と前提が異なる。何を証拠として受け入れるかは、対象の性質とRepository Rulesに依存する。一般的な十分性の基準は[未定義事項](./open-questions.md)である。

## PRの物理的構造

PRの最終スナップショットを次のように表す。

\[
P=(T,W,\mathcal K,X,V)
\]

| 記号           | 内容                                                |
| -------------- | --------------------------------------------------- |
| \(T\)          | Title                                               |
| \(W\)          | PR Body                                             |
| \(\mathcal K\) | 順序付きのCommitsと、それぞれのCommit Message・変更 |
| \(X\)          | Inline CommentsとGeneral Comments                   |
| \(V\)          | CI Results                                          |

Claimsには \(\mathcal Q\)、Commitsには \(\mathcal K\) を使い、記号の衝突を避ける。PR全体のDiffは、基準状態と変更後の状態の比較として観測される。

### GitHubの要素と役割

| 要素             | 物理的な役割                                     |
| ---------------- | ------------------------------------------------ |
| Title            | PRのタイトル                                     |
| Body             | PR全体に付属する文章                             |
| Commits          | 変更を順序付きで分割した単位                     |
| Commit Messages  | 各Commitのラベルと説明                           |
| Diff             | 変更前後のコードなどの差分                       |
| Inline Comments  | Diff上の位置に紐づくコメント                     |
| General Comments | PR全体に紐づくコメント                           |
| CI Results       | 自動検証の結果                                   |
| Code Comments    | ソースコードの一部。PRではDiffを通じて観測される |

GitHub上の配置だけで、論証上の役割は決まらない。Inline Commentは位置に紐づく機能であり、必ずしも局所的な説明やレビュー中だけ有効な情報に限定されない。Bodyには、複数ファイルにまたがる説明に加えて、PR全体の受け入れ判断に必要な情報を配置できる。

## 知識の保持

Retainedは、マージ後に必要な知識が失われず、将来の利用者が所定の経路で取得できるという完全性の条件である。

\[
\operatorname{Retained}(S_1,K_{\mathrm{required}})
\]

\(S_1\) は変更後の状態、\(K_{\mathrm{required}}\) は将来必要となる知識である。この表記では、利用者と想定するアクセス経路を評価の前提としている。必要な知識の範囲と、経路の成立条件の厳密化は[未定義事項](./open-questions.md)として残る。

すべての知識がWorking Tree内に直接記述されていることは要求しない。外部仕様やPR Recordなどへの明示的な参照によって、所定の経路で取得できる場合もある。ただし、情報がどこかに存在することだけでは、アクセス可能性は示せない。

### 三つのアクセス層

| 層           | 主な内容                                | 典型的な探索目的                 |
| ------------ | --------------------------------------- | -------------------------------- |
| Working Tree | コード、テスト、設定、ドキュメント      | 現在の状態を理解する             |
| Git History  | Commit、Commit Message                  | 変更箇所から、その変更理由を辿る |
| PR Record    | Body、Inline Comments、議論、CI Results | 特定の変更の詳細な論証を辿る     |

典型的なアクセス経路として、次を考える。

\[
\text{Code}\rightarrow\text{Commit}\rightarrow\text{PR}
\]

この経路は情報の優劣を表すものではない。利用者が何を知ろうとしているかによって、Working Treeの文書や外部仕様から直接辿る経路も適切になり得る。

## 情報の有効条件

説明 \(e\) の有効性を次のように表す。

\[
\operatorname{Valid}(e,S,E)
\]

\(S\) はリポジトリの状態、\(E\) は外部環境や依存関係の状態である。これは状態についての説明の表記であり、遷移についての説明には対象となる変更前後の状態や検証時点も明示する。状態依存と遷移依存を一般に区別する厳密な条件は、まだ定義していない。

## 認知負荷

PRの認知効率は、論証を追跡する際に、不必要な切り替え・記憶・推論を要求しないかという観点から評価する。

\[
C=(C_{\mathrm{switch}},C_{\mathrm{memory}},C_{\mathrm{inference}})
\]

各成分は異なる負担を表す。普遍的な順位や数値的な重みは定めず、利用者とタスクを評価の前提とする。

読者の知識・語彙と表現との距離は、PRに限らない[文章の読みやすさのモデル](../../documentation/expression/model.md)で扱う。論証の構造を整えても、使う言葉や前提を読者が理解できなければ、説明・判断へ進めない。PRでは両方の観点を組み合わせる。

### Repository Load

\[
H_{\mathrm{repo}}(S_f;K,T)
\]

最終リポジトリを理解・利用・変更するための認知負荷である。\(S_f\) は最終状態、\(K\) は利用者の知識、\(T\) は行うタスクを表す。

コードだけでなく、文書・テスト・履歴・参照経路も理解の負荷に関わるため、評価対象は実装 \(\mathcal I_f\) より広い最終状態として扱う。

### Review Load

\[
C_{\mathrm{review}}(\mathcal P,\pi,K_0)
\]

PRの変更を理解し、受け入れ判断を行うための認知負荷である。\(\mathcal P\) は対象となるPR群、\(\pi\) は提示・閲覧の順序、\(K_0\) はレビュー開始時の知識を表す。

Review Loadは、PR分割、Commit構造、提示順序、参照構造によって変化し得る。

必要な知識を取得できることと、その取得・理解・利用の負荷が低いことは別の条件である。例えば、必要な設計理由がすべて残っていても、多数のファイルに重複し、どれを参照すべきか判断しにくければ、保持の条件を満たしていても理解の負荷は高くなり得る。

## 品質の受け入れ条件

よいPRの条件を、次のように表す。

\[
\boxed{
\operatorname{Good}(P)=
\operatorname{Sound}(P)
\land\operatorname{Adequate}(P)
\land\operatorname{Structured}(P)
\land\operatorname{Retained}(S_1,K_{\mathrm{required}})
}
\]

\(S_1\) はPRによる変更後の状態である。この式は品質評価の枠組みを定めるものであり、各述語を機械的に判定する完全な手続きを与えるものではない。

| 条件       | 評価すること                                                 |
| ---------- | ------------------------------------------------------------ |
| Sound      | 構造間のマッピングについて、妥当な論証がある                 |
| Adequate   | Requirements、VO、Repository Rulesに対して十分である         |
| Structured | 変更と論証が適切に分割・配置され、不要な認知操作を要求しない |
| Retained   | 将来必要な知識を所定の経路で取得できる                       |

正当性、構造性、認知効率という観点に加え、マージ後の知識の保持を明示的な受け入れ条件とする。

### 評価で区別すること

- マッピングが存在することと、その対応が正しいこと。
- VOが網羅されていることと、各VOの証拠が十分であること。
- テスト成功と、すべての状態についての形式的証明。
- 知識が保持されていることと、その知識を理解する負荷が低いこと。
- 要求を採用した理由の正当性と、与えられた要求に対して実装を選択した理由。

Repository LoadはRetainedに吸収しない。必要な知識の完全性とは別に、最終状態の理解・利用・変更に必要な負荷を評価する。

各述語の判定条件や負荷の比較は形式化の途中にある。[未定義事項](./open-questions.md)を参照する。
